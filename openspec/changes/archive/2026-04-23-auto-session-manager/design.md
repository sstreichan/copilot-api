## Context

当前仓库已经具备三条主要 LLM 上游调用链，并在运行时共享部分全局状态；但与 Auto 路径相关的 `/models/session` 状态尚未被抽象成独立基础设施。现有代码可以直接构造并发送上游请求，也已经有与 `X-Initiator`、quota headers、smart-agent 相关的逻辑，但没有一个统一组件负责管理 `session_token`、`available_models` 与过期刷新。

前序真实后端实验已经确认以下事实：

- `/models/session` 会返回 `session_token` 与 `available_models`；
- 这些信息与 Auto 路径覆盖范围相关；
- 并非所有模型都应被一律附加 Auto session token；
- 为受覆盖模型尽量复用 Auto session，可能带来更高的 Auto 路径命中率，并保留 `discounted_costs` 相关的潜在附加收益；
- 若把这类逻辑散落在三条调用链内部，后续维护成本和行为漂移风险都会明显上升。

因此，本次设计目标不是复制 GitHub 内部完整 Auto 协议，而是在当前仓库内引入一个最小侵入、职责单一的 Auto Session Manager，作为 `/models/session` 状态的统一入口。

## Goals / Non-Goals

**Goals:**
- 以独立组件形式统一管理 `/models/session` 请求、`session_token` 缓存、`available_models` 缓存与过期刷新。
- 在服务启动阶段预热一次 Auto session 状态，使运行时一开始就有可用的模型覆盖信息与 session token。
- 让三条现有 LLM API 调用链仅在传入模型命中当前 `available_models` 时才获取并附着 `Copilot-Session-Token`，未命中时保持原行为不变。
- 将刷新时机定义为“调用方取 token 时按需刷新”，避免定时器轮询带来的状态竞争与额外复杂度。
- 为关键 Auto session 事件提供简洁的 `info` 级 `consola` 日志，至少覆盖模型命中/未命中与 token 刷新，并与仓库现有日志样式保持一致。
- 保持组件边界清晰，使未来若扩展到更完整的 Auto 行为时，优先在该组件附近演进，而不是继续向三条调用链扩散横切逻辑。

**Non-Goals:**
- 不实现完整的 `/models/session/intent` 编排与 `chosen_model` 路由决策。
- 不改变当前对外公开 API 或新增新的对外端点。
- 不承诺所有请求都必须走 Auto 路径；未命中 `available_models` 的请求继续按旧路径处理。
- 不把 `discounted_costs` 解释为已被完全证明的计费公式；该信号只作为潜在附加收益背景，而不是强制计费契约。

## Decisions

### 决策 1：引入独立的 Auto Session Manager，而不是把逻辑直接塞进三条调用链

选择：新增一个独立运行时组件，集中负责 `/models/session` 的状态管理与查询接口。

原因：
- `session_token`、过期时间与 `available_models` 属于同一运行时语义，应由同一组件持有；
- 三条调用链只需要一个统一查询接口，而不需要各自知道如何刷新、缓存或判定过期；
- 这更符合 SOC / SRP，也降低后续扩展或调试成本。

备选方案：
- 直接在 `create-messages`、`create-chat-completions`、`create-responses` 各自实现 `/models/session` 逻辑。

未采纳原因：
- 会产生重复状态、重复刷新与行为漂移；
- 后续若调整刷新规则，需在多条链路同时修改。

### 决策 2：启动时预热一次状态，但后续只在调用方取 token 时按需刷新

选择：组件启动时先拉取一次 `/models/session`，缓存 token 与模型列表；之后不使用后台定时器，而是在调用方请求 token 时检查是否过期，必要时同步刷新。

原因：
- 启动预热能让运行时尽早获得模型覆盖信息，避免第一笔命中请求才触发额外发现成本；
- 按需刷新比定时轮询更容易与调用方语义对齐，也更容易推导边界行为；
- 避免引入后台刷新与 shutdown/错误恢复之间的额外并发复杂度。

备选方案：
- 完全懒加载：第一次命中时才初始化。
- 定时后台刷新：按时间间隔主动更新 token 与模型列表。

未采纳原因：
- 完全懒加载会让首个命中请求承担更多延迟与状态初始化复杂度；
- 定时刷新会引入额外状态机、并发刷新冲突与不必要的后台流量。

### 决策 3：只有在传入模型命中当前 `available_models` 时才附着 `Copilot-Session-Token`

选择：Auto Session Manager 只为“受 Auto 覆盖的模型”提供 token 注入路径；未命中模型完全走旧行为。

原因：
- 这是最小侵入策略，能最大限度避免对不相关模型造成副作用；
- 与前序探索中“尽可能使用 Auto path，但不强行让所有请求都走 Auto”的目标一致；
- 使三条调用链改动点保持很薄，只需判断模型是否命中，再决定是否取 token。

备选方案：
- 对所有请求一律尝试附加 token。

未采纳原因：
- 会把 Auto session 逻辑扩大成全局默认行为，风险过高；
- 也不符合“未命中时一切保持原样”的设计边界。

### 决策 4：将 Auto Session Manager 定位为基础设施层，而不是完整 Auto Router

选择：本次只管理 `/models/session` 状态，不管理 `/models/session/intent`、`chosen_model` 推断或自动改写用户传入模型。

原因：
- 当前目标是提高 Auto session 复用率，不是复制完整内部协议；
- 这样可以在能力边界上保持克制，减少设计不确定性；
- 为后续若要扩展更完整 Auto 行为时预留演进空间。

备选方案：
- 一次性实现完整 Auto 三步协议与自动选模。

未采纳原因：
- 复杂度与风险明显更高；
- 不符合当前“least intrusive”的意图。

### 决策 5：使用现有 `consola` 模式输出简洁 `info` 级日志

选择：Auto Session Manager 的运行时日志使用仓库现有的 `consola`，仅在关键事件上输出简短 `info` 级日志，并沿用现有样式/配色约定。

原因：
- 仓库当前已经广泛使用 `consola` 作为运行时日志工具；
- 该能力需要可观测性，但不应引入一套新的日志框架或冗长日志格式；
- 命中/未命中与 token 刷新是定位 Auto 路径行为的核心事件，适合保留为简洁短日志。

备选方案：
- 不加日志，只依赖调试或测试定位行为。
- 使用独立 logger helper 或更高频率的 debug 级细粒度日志。

未采纳原因：
- 完全无日志会让运行时命中情况与刷新行为变得不透明；
- 另造日志风格会偏离现有仓库模式，也不符合“proper but concise short logging”的目标。

## Risks / Trade-offs

- [启动预热失败会导致初始缓存为空] → 组件需要允许“初始化失败但运行继续”，并让未命中或无缓存时安全回退到旧路径。
- [调用时刷新可能给首个过期后的命中请求带来额外延迟] → 接受这一代价，以换取实现简单与状态一致性；同时保持只有命中模型才触发该成本。
- [`available_models` 是会变化的运行时信号] → 每次刷新 token 时同步刷新模型列表，并明确缓存只是当前快照，不是永久契约。
- [错误地将所有收益归因于 `discounted_costs`] → 在设计与实现中只把它当作潜在附加收益背景，不作为硬编码成本公式。
- [三条调用链接入点不一致导致行为漂移] → 通过统一查询接口与测试覆盖，确保三条链路的“命中则取 token、未命中则不变”行为一致。
- [日志过多影响可读性] → 仅保留模型 hit/miss 与 token refreshed 等关键事件，使用简洁短句，并复用现有 `consola` 风格与颜色约定。

## Migration Plan

- 先新增 Auto Session Manager 及其状态接口，不改现有外部 API。
- 在启动路径接入一次初始化，并确保初始化失败时不会阻止服务启动。
- 逐条为三条现有 LLM API 调用链接入统一的“模型命中判断 + 条件取 token”逻辑。
- 在 Auto Session Manager 与三条调用链接入处补上简洁的 `info` 级 `consola` 日志，覆盖命中/未命中与刷新事件。
- 为命中/未命中、过期刷新、启动预热失败等路径补足测试。
- 若上线后观察到异常，可通过关闭该能力或移除接入点回退到旧路径；因为未命中时原行为本就保持不变，回退面相对集中。

## Open Questions

- 启动预热失败时，是否只记录日志并在后续首次命中时重试，还是需要显式暴露健康状态给现有状态系统。
- `session_token` 的过期判定应完全依赖 `/models/session` 响应中的过期字段，还是允许在缺失字段时采用更保守的刷新策略。
- 三条调用链的接入点应统一放在更上层的共享编排处，还是在各自的上游请求构造前做最薄接入；这一点需要在实现前结合现有代码组织再做最终落点确认。
- 日志文案应集中由 Auto Session Manager 输出，还是允许调用链在命中/未命中判定点补少量辅助日志；这一点需要在实现前结合现有代码结构确定最终归口。
